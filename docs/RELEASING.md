# 版本号规则（EmojiTot）

> 2026-11-21 定稿。起因：把 0.4.0 之后的一次增量改了版本号到 0.5.0，被用户指出「这不该跳 minor」。

## 一、采用语义化版本 SemVer 2.0.0

`MAJOR.MINOR.PATCH`，从右往左进位：

- **PATCH**（0.4.1 → 0.4.2 → … → 0.4.9 → 0.4.10）：修 bug、调布局、补文案、加一个小设置项。**这一类占绝大多数发布**。
- **MINOR**（0.4.x → 0.5.0）：成批的新能力落地，用户能明显感到「多了一块东西」（新页面、新功能板块）。一次 minor 必须能写出 3 条以上用户可感知的新能力，否则不配 minor。
- **MAJOR**（1.0.0）：接口/数据格式不兼容，或整体重写。EmojiTot 目前不该出现。

第三条数字**不是十进制小数**：0.4.9 之后是 **0.4.10**，不是 0.4.91，也不是 0.5.0。

## 二、本项目的具体约定

1. 每发一次 Release，**默认只加 PATCH**：0.5.0 之后是 0.5.1、0.5.2……
2. 只有满足「一次交付 ≥3 个用户可感知的新能力」才允许加 MINOR，且必须在 RELEASE NOTES 里逐条列出来。
3. 一个版本内允许包含多批并行支线的成果——合并成一次发布，仍然只加一个 PATCH。
4. tag 用轻量 tag `vX.Y.Z`，与 `package.json` 五处版本号一致。
5. 历史遗留：`v0.5.0` 是在规则定稿前发的，保留不改写；后续从 `0.5.1` 起按本规则走。

## 三、怎么防止再犯

`scripts/check-version.mjs` 读最近一个 tag 与当前 `package.json` 版本，做三条判断：

- 当前版本必须严格大于最近 tag；
- 若只增加 PATCH，通过；
- 若增加 MINOR/MAJOR，要求 `docs/RELEASE-NOTES.md` 里该版本号下至少 3 条 `- ` 开头的用户可感知条目，否则失败并提示「本次应只加 PATCH」。

发版前跑：`pnpm version:check`。
